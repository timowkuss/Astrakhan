# ASTRAKHAN

Рабочий интернет-магазин продуктового магазина: мобильный каталог, гостевое оформление без обязательного входа, серверная корзина, необязательный вход по WhatsApp OTP, профиль, тестовая оплата, заказы и админ-панель.

## Заказ без входа

Кнопка «Оформить заказ» открывает форму имени и телефона без WhatsApp-кода. Сервер создаёт отдельного гостя со случайной сессией в HttpOnly-cookie на 14 дней; гостевой телефон хранится как непроверенный контакт и не используется для поиска аккаунта. Покупатели с одинаковым введённым телефоном не получают доступ к заказам друг друга. После выхода, очистки cookie или истечения сессии доступ к гостевой истории теряется; сами заказы сохраняются у администратора. Вход через OTP остаётся доступен отдельно и не присоединяет гостевые заказы по номеру телефона.

Проверка: `npm run test:guest` — оформление без OTP, валидация телефона, отказ и повтор оплаты, суммы с сервера, идемпотентность, изоляция покупателей, доступ администратора и выход.

**Телефон магазина:** +7 702 313 53 83. **Часы:** 08:00–22:00, Asia/Almaty. Заказы ночью разрешены.

## Быстрый запуск

Нужен Node.js 22.13+ с npm. Проект проверен с Node.js 24.19 на Windows. Docker и отдельный сервер БД для локальной разработки не нужны.

```sh
npm ci
npm run setup:env
npm run build
npm run db:migrate
npm run db:seed
npm run dev
```

Открыть `http://localhost:5173`. Frontend и backend запускаются **одной командой**, API находится на том же origin в `/api/*`. Админка: `http://localhost:5173/admin`.

Если `npm` отсутствует в PATH, установите обычную поставку Node.js с npm. Наличие одного `node.exe` недостаточно для `npm ci`. В подготовленной рабочей папке зависимости уже установлены; доступен прямой запуск `node scripts/run-framework.mjs dev`.

Переменные окружения перечислены в `.env.example`. `setup:env` генерирует случайный `AUTH_SECRET`, не перезаписывая существующий `.env`. При ручном копировании `.env.example` обязательно замените пример секрета случайной строкой длиной не менее 32 символов. После изменения `.env` перезапустите dev-сервер при необходимости.

## Администратор

Публичной регистрации администраторов и встроенного пароля нет. Создать или обновить администратора локальной БД:

PowerShell:

```powershell
$env:ADMIN_LOGIN = 'admin'
$env:ADMIN_PASSWORD = 'ваш-уникальный-пароль-не-короче-12-символов'
npm run admin:create
Remove-Item Env:ADMIN_PASSWORD
```

macOS/Linux:

```sh
ADMIN_LOGIN=admin ADMIN_PASSWORD='ваш-уникальный-пароль-не-короче-12-символов' npm run admin:create
```

В текущей подготовленной папке уже создан `admin`; сгенерированный пароль находится **только локально** в `.local/admin-credentials.json`. Эта папка исключена из Git. Скрипт хранит в БД PBKDF2-хеш с индивидуальной солью и отзывает прежние сессии этого администратора при обновлении пароля.

## Тестовая покупка

1. Выберите подкатегорию в боковом меню или найдите продукт поиском. Поиск учитывает название, бренд, описание и характеристики, порядок слов и варианты `2.5` / `2,5`.
2. Добавьте штучные и весовые товары. Вес меняется шагами 0,5 кг; остаток проверяется на backend.
3. Откройте корзину и нажмите «Оформить заказ».
4. Введите любой корректный тестовый номер `+7 ...`. При `APP_MODE=development` код появится под формой. Реальное WhatsApp-сообщение не отправляется.
5. Код действует 5 минут, доступно 5 попыток. Повторная отправка — через 60 секунд; дополнительно действуют лимиты по номеру и IP. Новый код отменяет предыдущий, использованный код повторно не принимается.
6. После входа гостевая корзина переносится в серверную. При первом оформлении укажите ФИО; дополнительный телефон необязателен.
7. Выберите Kaspi или карту. В тестовом режиме можно проверить успех или отказ банка. Данные карты не запрашиваются, деньги не списываются.
8. После успеха откроется оплаченный заказ. В профиле есть «Мои заказы»; статусы обновляются каждые 15 секунд.
9. В админке откройте заказ: «Начать сборку» → «Заказ готов» → «Получен».

Для изменения/отмены покупатель звонит магазину. Самостоятельной кнопки отмены у клиента нет. В админке отмена активного заказа требует причину; полученный или уже отменённый заказ повторно отменять нельзя.

## Стек и структура

- React 19, TypeScript, Next-совместимая маршрутизация через Vinext/Vite.
- Cloudflare Workers runtime; локально Miniflare/Wrangler.
- SQLite/D1, Drizzle для схемы и миграций, prepared SQL для запросов.
- R2 для фотографий, локальное устойчивое R2-хранилище при разработке.
- Radix/Shadcn для доступных select, sheet, dialog, tabs; Lucide и Sonner.

```text
app/storefront.tsx          Каталог, корзина, вход, оформление, профиль, заказы
app/admin-ui.tsx            Заказы, товары, категории, фотографии, журнал
app/api/[...path]/route.ts  API, серверная валидация и проверка ролей
components/shop/           Общие контролы магазина
lib/client-api.ts          Обработка сетевых ошибок клиента
lib/domain.ts              Форматирование, вес, суммы, поиск, переходы статусов
lib/server/db.ts           Доступ к D1 и транзакционным batch
lib/server/security.ts     Сессии, HMAC OTP, PBKDF2, rate limits, Origin
lib/server/orders.ts       Корзины, атомарное оформление, статусы и снимки
lib/server/catalog.ts      Серверная выборка каталога
lib/server/providers.ts    WhatsApp, payment и product source contracts
lib/server/request.ts      Ограничение размера и чтение HTTP-запросов
db/schema.ts               Реляционная схема
drizzle/                   Миграции SQL и их метаданные
scripts/seed.mjs            Идемпотентное заполнение тестовыми продуктами
tests/                     Интеграционные и конкурентные проверки
public/products/           Оптимизированные демонстрационные WebP-фото
```

В starter зафиксирован `vinext@1.0.0-beta.5`. Сборка и основные сценарии проверены локально; перед коммерческим запуском необходимы staging-проверка runtime и подключение реальных провайдеров. Это не утверждение о готовности к приёму реальных денег.

## База данных и миграции

Есть Store, User, Profile, Admin, Session, AuthChallenge, RateLimit, Brand, Category, Product, ProductImage, Cart, CartItem, CartMerge, Order, OrderItem, Payment, StatusHistory и AuditLog. Основные связи — foreign keys, категории дополнительно защищены триггерами двухуровневой иерархии. Индексы используются для клиента, статуса, категории, уникальности оплат и повторных запросов.

```sh
npm run db:generate    # После изменения db/schema.ts
npm run db:migrate    # Применить только новые локальные миграции
npm run db:seed       # Добавить отсутствующие демонстрационные записи
```

Миграции применяются через стандартный журнал Wrangler `d1_migrations`. Повторный `db:migrate` не пересоздаёт таблицы. Применённые миграции не изменяйте — добавляйте новые. Seed отделён от миграций и не перезаписывает цены, остатки или фотографии существующих товаров.

Локальная БД и файлы: `.wrangler/state`. Закрытие браузера/сервера не удаляет корзины и заказы. Удаление этой директории уничтожит локальные данные. Данные не входят в Git; для переноса и резервирования используйте экспорт D1 и резервную копию R2.

Все деньги в БД — целые тиыны. В JSON API и интерфейсе цены представлены в тенге. Сумма каждой позиции округляется до тиына. Для весового товара `quantity=1` означает 0,5 кг, `quantity=3` — 1,5 кг. Для штучного `quantity=1` означает одну штуку. `stock` использует ту же целочисленную шкалу. Админский интерфейс переводит килограммы в эти шаги автоматически. Единицу уже созданного товара менять нельзя: для другой единицы создайте новую позицию.

## Гарантии оформления

- Сумма считается по данным БД; переданное клиентом поле total не используется.
- В OrderItem копируются название, бренд, фотография, единица, цена, количество и сумма. История не зависит от будущих изменений Product.
- Order, OrderItem, Payment, история статуса, списание остатка и очистка корзины записываются в одном D1 batch с откатом при ошибке.
- Уникальны `(user_id, idempotency_key)` и `(user_id, cart_version)`. Повторный запрос возвращает тот же заказ. Версия корзины и DB-триггер исключают оплату устаревшего состава.
- Перенос гостевой корзины имеет отдельный идемпотентный ключ. Повтор запроса после потери ответа не удваивает количество.
- Триггеры запрещают отрицательный остаток. Два покупателя не могут забрать последнюю единицу одновременно.
- Изменение статуса использует версию заказа. Повторная/конкурентная отмена не возвращает остатки дважды.
- HttpOnly + SameSite cookies, Secure при HTTPS, серверные роли и ownership-проверки. Сессии хранятся хешированными, действуют 14 дней и отзываются при выходе.
- Admin CRUD, смена статусов и ручные корректировки записываются в audit log. Корректировка требует пояснение после согласования с клиентом.

Если состав оплаченного заказа изменён, `paid_total` остаётся прежним, а `total` отражает согласованный состав. Разница явно показана клиенту и администратору. **Возвраты и доплаты пока не автоматизированы.** При отмене Payment отмечается `refund_required`: сотрудник должен обработать возврат отдельно.

## Фотографии

В разделе «Товары» загрузите одну JPEG/PNG/WebP-фотографию. Браузер уменьшит её до 900 px и перекодирует в WebP; сервер ограничивает размер файла 1,5 МБ, проверяет MIME и сигнатуру и сохраняет в R2. SVG/HTML не принимаются. URL старых фотографий сохраняются для снимков заказов.

Демонстрационные фотографии уже находятся в репозитории и не требуют доступа к сторонним сайтам при просмотре. Источники и ограничения использования — в `PHOTO-CREDITS.md`. Для коммерческого запуска замените их собственными точными фотографиями ассортимента.

## WhatsApp позже

Точка подключения: `WhatsAppProvider` в `lib/server/providers.ts`.

- DevelopmentWhatsAppProvider включён только при `APP_MODE=development`; API возвращает код в developmentCode исключительно в этом режиме.
- HttpWhatsAppProvider — подготовленный адаптер к вашему HTTPS-сервису отправки. Он передаёт `{phone, code, expiresIn}` с Bearer-токеном.
- Задайте `WHATSAPP_ENDPOINT`, `WHATSAPP_TOKEN` и адаптируйте запрос к реальному провайдеру/одобренному authentication template. Это не готовая интеграция с Meta или конкретным коммерческим поставщиком.
- Проверка кода, TTL, попытки, одноразовость и лимиты остаются в auth service и не зависят от транспорта.
- При `APP_MODE=production` тестовый код не выдаётся. Без настроенного провайдера вход завершится понятной ошибкой; вымышленных ключей нет.

## Kaspi и банковская карта позже

Точка подключения: `PaymentProvider` и `paymentProvider()` в `lib/server/providers.ts`, orchestration — `checkout()` в `lib/server/orders.ts`.

Сейчас работает только явно обозначенный TestPaymentProvider. При `APP_MODE=production` приём платежей блокируется до установки настоящего адаптера. Простая замена значения env не включает реальную оплату.

Для реального провайдера необходимо реализовать hosted payment session/redirect и серверное подтверждение: подпись callback, сверку order/reference, суммы и валюты KZT, уникальность event ID и повторную доставку. Сначала создавайте/резервируйте pending payment intent; после проверенного подтверждения атомарно переводите заказ в paid. Используйте стабильный idempotency key и API идемпотентности самого провайдера. Не переносите сетевое списание денег внутрь SQLite-транзакции и не считайте браузерный redirect доказательством оплаты. Отдельно подключите refund/reconciliation. Данные карты остаются у платёжного провайдера.

## Внешняя база / 1С позже

UI работает через `/api/catalog`, а не с 1С. `ProductSource`/`LocalProductSource` в `providers.ts` и `catalog.ts` задают серверную границу. Будущий импорт должен сопоставлять `external_id`, обновлять локальные товары, цены и остатки, сохранять управляемые магазином фотографии/категории и не изменять OrderItem. Синхронизация и API 1С в V1 отсутствуют.

Store уже связан с Product, Cart и Order. Сейчас используется `main`; для трёх точек добавьте выбор текущей точки на сервере, складские остатки по точкам и права сотрудников по store_id. Клиентские адреса или доставку это не требует.

## Проверки

При запущенном локальном сервере:

```sh
npm run typecheck
npm test
npm run test:concurrency
npm run test:auth
npm run build
```

Тесты используют `.local/admin-credentials.json`, тестовые номера и **изменяют только локальную тестовую БД**. Для своего администратора создайте этот локальный JSON с полями login/password или передайте ADMIN_LOGIN/ADMIN_PASSWORD. Не запускайте сценарии над рабочим магазином. Лимиты OTP действуют и в разработке; частые повторы тестов могут закономерно получить 429.

Проверяется поиск, OTP/cooldown/повторное использование, перенос корзины, веса, отсутствие товара, отклонённая оплата, idempotency, пересчёт суммы, snapshots, права, статусы, корректировки, отмена, категории, аудит, CSRF, конкурентное оформление/остатки, загрузка фото и отклонение поддельного файла. Полный пользовательский сценарий и действия администратора также проверены через браузер.

## Сборка и размещение

```sh
npm run build
npm start -- --port 5174
```

Вторая команда запускает собранный Worker локально. Это **не публикация в интернете**. В текущей работе внешняя публикация не выполнялась.

Для отдельного Cloudflare deployment используйте результат `dist/server/index.js` и `dist/client`, настоящие D1/R2 bindings вместо локальных placeholder IDs, примените миграции и задайте production secrets в конфигурации хостинга. `wrangler.local.json` предназначен только для локальной разработки; не публикуйте его как конфигурацию production. `.openai/hosting.json` — сохранённая регистрация проекта в Sites, не признак размещённого рабочего магазина.

Перед коммерческим запуском нужны реальные WhatsApp/payment adapters, HTTPS origin в APP_ORIGIN, новый production AUTH_SECRET, резервное копирование, реальные товары/фотографии и проверка сценариев на staging. Секреты, `.env`, `.local` и `.wrangler` в репозиторий не добавляйте.
